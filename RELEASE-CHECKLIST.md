### Rate limits (lab PCs share one public IP)

`trust proxy` is set to 1 hop in production, so limits are per real client IP.
Measured in the browser test: about 5 API calls per page view. The default
`RATE_LIMIT_MAX_REQUESTS=300` per `RATE_LIMIT_WINDOW_MINUTES=15` therefore allows only
about 60 page views per 15 minutes **for the whole lab**.

Recommendation:
- `RATE_LIMIT_MAX_REQUESTS` = 400 × (number of staff PCs), e.g. **3000** for 6–8 PCs.
  Keep `RATE_LIMIT_WINDOW_MINUTES=15`.
- Keep `PUBLIC_RATE_LIMIT_MAX_REQUESTS=60` (public website forms are separate).
- Login, campaign and test-send routes keep their own stricter limits (unchanged).
- The frontend now keeps the session on a 429 (it no longer logs users out when
  the limit is hit).

## 6. Known remaining risks
- **zod 3.25.x — 1 high advisory** (GHSA-mrhx-c7xc-m3w5, memory use on oversized
  constrained collections). Mitigated: every JSON / form body is capped at 2 MB, and
  validators cap array sizes (for example 5000 list entries). A trial upgrade to zod 4.6.7
  in an isolated copy **failed**: `whatsapp.validator.js` uses `.innerType()` on refined
  schemas (removed in v4), which breaks the WhatsApp and campaign routes at load, and the
  suite then hangs. A real migration is a separate task: see
  `backend-transfer/ZOD4-MIGRATION-PLAN.md`, then fix `.innerType()`, `required_error`
  (5 uses), `invalid_type_error` (4) and `errorMap` (1), and run the full suite.
- Meta campaign delivery is not implemented (Twilio and MSG91 are).
- Customer search uses escaped regular expressions (safe). For collections much larger
  than about 100k customers, consider a text index for performance.
